# Solar91 O&M — reliability and scaling update

## Install safely

Use the combined changes-only archive if starting from the supplied original Solar91 ZIP. Use the incremental performance archive only if the previous PM Gradient update is already installed. Both archives retain project-relative paths. Back up the current deployment and database; apply the files on a staging branch first. The combined archive includes PM migration 051 and optional supervisor migration 052; apply both before deploying the app. No additional performance-only migration is required. Do not copy .env.example over your live .env or paste real credentials into the repository. Deploy the frontend and backend together; the asset hashing already present in the project invalidates changed scripts. Verify the current build in the health/version endpoint.

## What this patch actually changes

- Process-local token buckets for API peer and aggregate request rates, plus separately throttled verified Clerk users' reads and writes. The active-request cap rejects excess work with 503 and Retry-After; 429 indicates a rate-limit rejection. A fifth of active slots is reserved from GET/HEAD traffic so saves are less likely to be starved. OPTIONS and static files bypass this API limiter. Bounded bucket storage avoids unbounded key growth. Limits are per worker, not deployment-wide, and do not stop upstream volumetric attacks.
- Existing PostgreSQL pool retains a 5+2 connection cap per worker and now waits at most 8s for a pooled connection by default, returning a readable 503 if exhausted. The psycopg connection timeout is 8s. Existing timing, idle-aware connection checks and recycling remain. This is not a universal SQL statement timeout.
- Shared browser JSON transport deduplicates overlapping GETs, allows five concurrent reads (two on detected 2G/3G/Data Saver), bounds the waiting queue to 64 with a 15s wait limit, and retries a failed read at most once for transient network/429/502/503/504 failures with jitter and Retry-After handling. Each read attempt is bounded by 45s and a write by 60s, including body download. Auth refresh on 401 retains existing behaviour. No blind automatic replay of a potentially committed write; a lost response requires checking the record before retrying. Existing direct file-transfer paths are not all routed through this JSON transport.
- Successful JSON writes invalidate client-side dashboard/plant/period caches; refresh is coalesced rather than issuing a separate full reload for every entry. Server-side legacy washing and issue pulse caches still invalidate on writes or uncertain failures; rejected rate-limit requests do not flush them. The Overview checks versions only while visible, backs off on failure, polls more slowly on weak connections and performs a full refresh after five minutes to recover changes that do not alter the existing max-timestamp version token. The version endpoint covers the existing Overview sources, not every table in the portal. Other users see updates on the next applicable successful poll, not instant push.
- Navigation load tokens are incremented even when the destination is already loaded, preventing late module responses from replacing a newer page. Prefetch only common field pages and skip 2G/3G/Data Saver. Existing hashed static assets, compression, pagination and lazy image paths are retained.
- PM portfolio now asks for summary-only records, omitting checklist text, observations and review details until the individual plant is opened. The database query also omits those fields. Plant rows are indexed by plant instead of repeatedly scanning the fleet. PM retains the last successful same-month view during refresh, uses a bounded in-memory short-lived cache for plant/calendar navigation, records the server's data-check timestamp, and polls only while the page is visible and not being edited. Failed refreshes label prior data as stale, not zero. Active checklists and action-form text are not replaced by background polling. Successful PM submissions and approvals reload the server state; permission checks and sequencing stay server-side. The main Overview also reads the scoped monthly checklist counts in one grouped query and includes the checklist change timestamp in its version check. When assigned checklist records exist, its PM tile shows approved checklist progress and labels the separate legacy work-order count; it never sums the two systems.
- Connection indicator distinguishes connected/offline/interrupted/busy and reduced-motion preference suppresses the targeted skeleton animation. Existing PM gradient design is unchanged.

## Starting configuration — measure before raising limits

| Setting | Default | Meaning |
|---|---:|---|
| TRAFFIC_GUARD_ENABLED | true | Enable the safety guard outside tests |
| API_MAX_ACTIVE | 20 | Active API requests per worker, including writes |
| API_IP_PER_MINUTE / API_IP_BURST | 600 / 100 | Per peer, includes shared site-office NAT users |
| API_GLOBAL_PER_MINUTE / API_GLOBAL_BURST | 1800 / 150 | Worker-wide ceiling |
| API_USER_READS_PER_MINUTE | 180 | Per verified user, burst capped at 40 |
| API_USER_WRITES_PER_MINUTE | 60 | Per verified user, burst capped at 12 |
| DB_POOL_SIZE / DB_MAX_OVERFLOW | 5 / 2 | Maximum seven DB connections per worker |
| DB_POOL_TIMEOUT_SECONDS | 8 | Pool checkout deadline |
| DB_POOL_RECYCLE_SECONDS | 1800 | Recycle pooled connections |
| DB_POOL_PRE_PING / DB_PING_IDLE_SECONDS | true / 10 | Idle-aware health check |
| SLOW_REQUEST_MS | 1000 | Existing slow-request log threshold |

Treat these as initial safeguards, not throughput promises. Keep API and Supabase in a compatible nearby region; check startup RTT and query timings. Connection budget = instances × workers × (pool size + overflow), plus background jobs, admin sessions and other services. E.g. two single-worker instances with defaults can use 14 connections; verify actual pooler and PostgreSQL quotas before scaling. Do not increase worker count or connection limits independently. Run scheduled jobs in one designated process or use distributed job leases. If many engineers share a NAT or proxy, monitor peer-level 429s and tune to measured needs. Configure trusted proxy forwarding at the platform boundary; never trust arbitrary incoming X-Forwarded-For. Use an edge/API gateway with global and authenticated-user limits (or distributed Redis counters) before multiple replicas; local buckets cannot coordinate across processes. Add request-size limits and WAF protection at the edge; use only validated, bounded uploads.

## Scale roadmap / production acceptance (not yet deployed)

1. Use a paid always-on service for field-critical operation; separate web traffic from heavy imports, report exports, image processing and scheduled jobs with a durable job queue when load justifies it. Set timeouts and quotas per workload, with job IDs and status instead of a long-held HTTP request. Confirm retention/backups, restore drills and least-privilege service credentials.
2. Instrument p50/p95/p99 API latency, first-page usability, response bytes, request rate, pool wait, database RTT, worker memory/CPU, 429/503/5xx rate and write-to-visible delay. Use current Server-Timing, X-Request-ID and slow logs; add central monitoring and alerts. Candidate staging goals (not measured): warm key reads p95 <1s, usable first view <3s on good mobile data, cached navigation <300ms, own saved result visible <2s when network/server permit, no lost/duplicate writes, no sustained pool exhaustion. Define separate slow-network targets; do not compare offline latency to broadband.
3. Run the existing `docs/LOAD_TESTING_GUIDE.md` and guarded `loadtests` runner against staging with synthetic data only; add PM summary and checklist/action cases before measuring full workflow capacity. Test 1, 25, 50, 100 users, then measured growth; cover 3G, high latency, packet loss, disconnect/reconnect, low-end Android and desktop browsers. Test long-duration soak, simultaneous writes, failed responses after commit, rollback and restore. Never stress production.
4. For future scale, use query plans and scoped composite indexes on observed hot paths, cursor pagination/virtualization for large lists, compact materialized aggregates only with a tested invalidation/version model, and shared role-scoped caches or push/SSE if measured polling cost warrants it. Avoid cache keys that omit user scope, role, plant, month, filters or permissions. Direct SQL edits must preserve existing transaction/audit rules; max timestamp change detection is imperfect, which is why periodic reconciliation matters.
5. Offline operation is not implemented as durable sync. Existing visible data can be retained in memory and PM input survives a failed save while the form stays open, but reload/navigation can lose unsaved input and a new offline visit cannot fetch private records. Full offline recording would need role-scoped encrypted local drafts, stable client-generated operation IDs, server idempotency constraints, conflict review and a durable sync protocol. Do not mark records completed until server acknowledgement. No sensitive data is newly persisted in localStorage/IndexedDB or service-worker caches by this patch.
6. Overview's primary PM tile displays monthly checklist progress where assigned data exists; the legacy work-order counts, legacy trend and health classification remain separate. Do not sum them without reconciling the work orders. Existing equipment outside the approved checklist scope is unchanged.

## Rollback

Keep the deployed commit and environment settings. Roll back application files to the preceding known-good commit if a regression occurs; do not drop PM tables with live records. You can temporarily tune limits after checking capacity; disabling the traffic guard removes its protection and is not recommended under overload. No production deployment, live SQL, load test or uptime guarantee was performed here.
