# PM checklist → corrective Site Issues

* A valid **Submit for approval** creates one corrective ticket per Not OK or Abnormality checkpoint, not on selection or preview. OK and N/A do not generate tickets. Existing date, plant scope, sequence and observation validation stay in place. Site Engineers and Assignees can submit eligible work; only O&M Heads approve or return.
* Ticket stores the plant, equipment and unit ID, checklist wording, result, observation and inspection date. Combined PM sections route using explicit equipment headings; GSS uses the existing GSS responsibility aliases. Ordinary checks route by the PM equipment. The active work category name is used where it matches. No category is silently added to the master.
* Existing Site Issue routing hierarchy (plant + equipment, plant-wide, global equipment, default, with eligible backups) applies. If nobody is configured, the ticket is Open and unassigned, and active O&M Heads are notified. A PM finding is not proof of downtime: severity defaults to Medium and equipment_running remains unknown. The normal default issue deadline applies. The Head may correct the ticket using existing Edit.
* `issues.source_task` contains `PM:<activity UUID>:<checklist item UUID>`, and `legacy_payload.pm_source` preserves the original observation and source. The Site Issue table and drawer show a From Preventive Maintenance label. PM photo evidence remains in the originating checklist; no duplicate Storage objects are created.
* Deterministic ticket IDs and the shared advisory lock prevent duplicate tickets on return/resubmission, including after an issue has been archived or closed. Changed observations remain on the PM checklist; existing tickets are not overwritten or reopened. A newly failed checkpoint generates a new issue. No historical PM backfill.
* PM submission, new tickets, issue audit history, and issue notifications commit together. An error rolls back the batch; existing standalone PM action notification is still delivered by its existing post-commit mechanism. Notification recipients are only the assigned issue owner and O&M Heads; PM owner receives the separate normal PM event. Use the existing notification popup/polling, not a second service.
* No migration. Source metadata uses existing columns. Healthy submissions skip the corrective bridge entirely; page-load paths do not resolve assignments or query PM sources. Multi-equipment batches use one bounded routing snapshot, one category/deadline lookup, one ticket-number allocation, and one indexed existing-ticket lookup. Each new ticket has its own history and notification records.
